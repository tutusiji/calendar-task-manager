## 2. 问题一：巨型 Store（God Store）

### 现状

`lib/store/calendar-store.ts` 一个文件 **1638 行**，承担了 6 种不同职责：

```
calendar-store.ts
├── 数据获取 (fetchTasks/fetchProjects/fetchUsers/fetchTeams/fetchAllData)
├── 业务操作 (addTask/updateTask/deleteTask/addProject/...)
├── 权限校验 (canCreateTaskInProject/canEditTaskInProject)
├── 拖拽状态 (dragState/dragMoveState + 8 个方法)
├── UI 状态 (viewMode/navigationMode/mainViewMode/listGroupMode/...)
└── 导航逻辑 (setSelectedTeamId/setSelectedProjectId/setNavigationMode)
```

### 问题

1. **任何修改都影响整个 store**，多人协作容易冲突
2. `addTask` 方法内联了权限检查、API 调用、数据刷新、toast 提示，**一个方法 70 行**
3. 拖拽逻辑（`startDragCreate`/`startDragMove`/`updateDragMove`/`endDragMove` 等）和业务数据完全耦合
4. "根据 navigationMode 决定 fetchTasks 参数" 的逻辑在 `fetchAllData`、`addTask`、`updateTask`、`deleteTask`、`stopRecurringTask` 中**重复出现 5 次**

### 优化方案：Zustand Slices Pattern

```typescript
// lib/store/slices/task-slice.ts
interface TaskSlice {
  tasks: Task[];
  isLoadingTasks: boolean;
  fetchTasks: (filters?: TaskFilters) => Promise<void>;
  addTask: (task: TaskCreateInput) => Promise<void>;
  updateTask: (id: string, updates: TaskUpdateInput) => Promise<void>;
  deleteTask: (id: string) => Promise<void>;
}

export const createTaskSlice: StateCreator<StoreState, [], [], TaskSlice> = (set, get) => ({
  tasks: [],
  isLoadingTasks: false,
  fetchTasks: async (filters) => { ... },
  addTask: async (task) => {
    // 权限校验 → 调用 API → 乐观更新 store
  },
  ...
})

// lib/store/slices/drag-slice.ts
interface DragSlice {
  dragState: DragState;
  dragMoveState: DragMoveState;
  startDragCreate: (...) => void;
  updateDragCreate: (...) => void;
  endDragCreate: () => ...;
  startDragMove: (...) => void;
  updateDragMove: (...) => void;
  endDragMove: () => void;
  ...
}

// lib/store/index.ts — 组合所有 slice
export const useCalendarStore = create<StoreState>()(
  persist(
    (...args) => ({
      ...createTaskSlice(...args),
      ...createProjectSlice(...args),
      ...createTeamSlice(...args),
      ...createUISlice(...args),
      ...createDragSlice(...args),
      ...createAuthSlice(...args),
    }),
    { ... }
  )
);
```

### 附：消除重复的导航过滤逻辑

当前每次操作后都要写这段代码：

## 3. 问题二：两套 HTTP 客户端并存

### 现状

| 文件 | 库 | 行数 | 使用情况 |
|------|----|------|---------|
| `lib/api-client.ts` | 原生 fetch | 607 | **实际使用中** (store + 组件) |
| `lib/request.ts` | axios | 300 | **几乎未使用** |

两套都在做相同的事：token 注入、错误处理、响应格式解析。

### 优化方案

**保留 `api-client.ts`（fetch），删除 `request.ts`（axios）。**

理由：
- `api-client.ts` 已经被所有代码实际引用
- 原生 fetch 无需额外依赖，bundle 更小
- axios 的优势（拦截器、取消请求）在当前项目中未被使用

如果团队更熟悉 axios，也可以反过来统一到 `request.ts`，但要确保所有 `import { taskAPI } from './api-client'` 的地方都迁移。

## 4. 问题三：认证状态散落多处

### 现状

认证信息存在于三个独立位置：

```typescript
// 1. localStorage — 直接读写
localStorage.getItem("currentUser")   // page.tsx:53, calendar-store.ts:518
localStorage.getItem("auth_token")    // api-client.ts:27, store deleteTask:918

// 2. Zustand store
useCalendarStore(state => state.currentUser)

// 3. JWT Token
getToken()  // 从 localStorage 读取
```

`page.tsx` 检查一次 localStorage，`fetchAllData` 又从 localStorage 解析一次用户。`deleteTask` 方法甚至绕过了 `api-client.ts` 直接用 `fetch` + `localStorage.getItem("auth_token")` 发请求。

### 优化方案

```typescript
// lib/store/slices/auth-slice.ts
interface AuthSlice {
  currentUser: User | null;
  isAuthenticated: boolean;
  login: (credentials: LoginCredentials) => Promise<void>;
  logout: () => void;
  initializeAuth: () => boolean; // 从持久化恢复，返回是否有效
}

// Zustand persist 只持久化 currentUser，token 单独管理
// api-client.ts 的 getToken() 改为从 store 读取（或保持 localStorage 但统一入口）
```

原则：
- **Store 是唯一数据源**，组件通过 `useCalendarStore` 读取用户
- 登录/登出只通过 store action 操作
- `page.tsx` 不再直接读 localStorage，改为 `useCalendarStore.initializeAuth()`

## 5. 问题四：API Route 缺乏复用

### 现状

每个 API route 都在重复：

```typescript
// 1. 认证
const auth = await authenticate(request)
if (auth.error) return auth.error

// 2. 组织校验（部分 route 有）
const user = await prisma.user.findUnique({ where: { id: auth.userId } })
const targetOrgId = user?.currentOrganizationId
const isMember = await prisma.organizationMember.findUnique({ ... })

// 3. 业务逻辑（200+ 行内联）
```

### 优化方案：高阶函数 + Service 层

```typescript
// lib/api/with-auth.ts
export function withAuth(handler: (req: NextRequest, userId: string) => Promise<NextResponse>) {
  return async (request: NextRequest) => {
    const auth = await authenticate(request)
    if (auth.error) return auth.error
    return handler(request, auth.userId)
  }
}

// lib/api/with-org.ts
export function withOrg(handler: (req: NextRequest, userId: string, orgId: string) => Promise<NextResponse>) {
  return withAuth(async (request, userId) => {
    const orgId = await resolveOrgId(userId)
    if (!orgId) return validationErrorResponse('未指定组织')
    // 校验组织成员关系...
    return handler(request, userId, orgId)
  })
}

// app/api/tasks/route.ts — 优化后
export const GET = withOrg(async (request, userId, orgId) => {
  const filters = parseTaskFilters(request)
  const tasks = await taskService.getTasks(orgId, userId, filters)
  return successResponse(tasks)
})

export const POST = withOrg(async (request, userId, orgId) => {
  const body = await request.json()
  const task = await taskService.createTask(userId, orgId, body)
  return successResponse(task, '任务创建成功', 201)
})
```

## 6. 问题五：权限校验前后端不一致

### 现状

前端 store 中的权限检查：

```typescript
// calendar-store.ts:611-635
if (currentUser) {
  const project = projects.find((p) => p.id === task.projectId);
  if (project) {
    const hasPermission = canCreateTaskInProject(currentUser.id, project, assigneeIds, currentUser.isAdmin);
    if (!hasPermission) { showToast.error(...); throw new Error(...); }
  }
}
```

后端 API route 中的权限检查：

```typescript
// app/api/tasks/route.ts:401-429
const canCreateForAssignees = canCreateTaskInProject(auth.userId, {
  creatorId: project.creatorId,
  taskPermission: project.taskPermission,
  memberIds: project.members.map(m => m.userId),
}, assigneeUserIds)
```

两处调用的是同一个 `canCreateTaskInProject` 函数（来自 `lib/utils/permission-utils.ts`），**但传入参数结构不同**：前端传的是 store 中的 project 对象，后端传的是从数据库查询后手动构造的对象。如果 project 接口变化，容易不一致。

### 优化方案

确保前后端使用完全相同的函数签名，并抽取统一的参数构造逻辑：

```typescript
// lib/utils/permission-utils.ts — 保持不变，但添加类型约束
export interface PermissionContext {
  creatorId: string;
  taskPermission: TaskPermission;
  memberIds: string[];
}

export function canCreateTaskInProject(
  userId: string,
  project: PermissionContext,  // 明确类型
  assigneeIds: string[],
  isAdmin?: boolean
): boolean { ... }
```

## 7. 问题六：数据刷新策略低效

### 现状

每次 CRUD 操作后全量 refetch：

```typescript
// addTask 成功后
Promise.all([
  task.projectId ? get().fetchProjects() : Promise.resolve(),
  task.teamId ? get().fetchTeams() : Promise.resolve(),
  // 全量重新获取任务列表
  (async () => {
    if (navigationMode === "team" && selectedTeamId) {
      await get().fetchTasks({ teamId: selectedTeamId });
    } else if (...) { ... }
  })(),
])
```

同时 `fetchTasks` 里强制 loading delay：

```typescript
// calendar-store.ts:309-310
const loadingDelay = useLoadingDelay();
loadingDelay.start();
// ...
await loadingDelay.waitForMinDuration(); // 即使数据已经返回，也要等
```

### 优化方案

**1. 乐观更新 (Optimistic Update)**

```typescript
addTask: async (task) => {
  // 1. 乐观更新：立即在 store 中添加任务
  const optimisticTask = { ...task, id: `temp-${Date.now()}` }
  set(state => ({ tasks: [...state.tasks, optimisticTask] }))

  try {
    // 2. 调用 API
    const created = await taskAPI.create(task)
    // 3. 用真实数据替换乐观数据
    set(state => ({
      tasks: state.tasks.map(t => t.id === optimisticTask.id ? created : t)
    }))
  } catch (error) {
    // 4. 回滚
    set(state => ({
      tasks: state.tasks.filter(t => t.id !== optimisticTask.id)
    }))
    throw error
  }
}
```

**2. Loading Delay 只用于初始加载**

```typescript
// 初始加载用
fetchAllData: async () => { ... loadingDelay.start() ... }

// CRUD 操作不用
addTask: async (task) => { /* 直接调 API，不加 delay */ }
```

## 9. 问题八：安全与环境配置

### 9.1 JWT Secret 硬编码

```typescript
// lib/auth.ts:6
const JWT_SECRET = process.env.JWT_SECRET || 'your-secret-key-change-this-in-production'
```

如果部署时忘记设置环境变量，就用了弱密钥。

**修复**：启动时校验环境变量，缺失则直接报错退出。

```typescript
const JWT_SECRET = process.env.JWT_SECRET
if (!JWT_SECRET) {
  throw new Error('JWT_SECRET environment variable is required')
}
```

### 9.2 Token 有效期过长，无刷新机制

当前 token 有效期 **90 天**，没有 refresh token，没有吊销机制。

**建议**：
- Access Token 缩短到 1-7 天
- 增加 Refresh Token（有效期 30 天）
- 或者接受长 token 但增加黑名单机制（Redis 存储已吊销 token）

### 9.3 无 Rate Limiting

登录接口没有防暴力破解。

**建议**：在 `app/api/auth/login/route.ts` 加入简单的 rate limiting（可以用内存计数器，生产环境用 Redis）。

## 11. 问题十：缺少错误边界

### 现状

没有 React Error Boundary。如果任何组件渲染出错，整个页面白屏。

### 优化方案

```tsx
// components/error-boundary.tsx
'use client'
import { Component, type ReactNode } from 'react'

interface Props {
  children: ReactNode
  fallback?: ReactNode
}

interface State {
  hasError: boolean
}

export class ErrorBoundary extends Component<Props, State> {
  state = { hasError: false }

  static getDerivedStateFromError() {
    return { hasError: true }
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? <div>出错了，请刷新页面</div>
    }
    return this.props.children
  }
}

// app/page.tsx 中使用
<ErrorBoundary fallback={<ErrorPage />}>
  <MainContent />
</ErrorBoundary>
```

## 附录：不需要做的事情

以下方案经过分析，**不建议采用**：

| 方案 | 原因 |
|------|------|
| 用 Python/FastAPI/Flask 重写后端 | 当前 Next.js API Route 已经能满足需求，引入新语言增加运维成本 |
| 用 Koa/Express/NestJS 重写 | Next.js 内置的 API Route 与前端同构，迁移无收益 |
| 引入 DDD 架构 | 项目规模不需要 DDD 的复杂度，当前的 CRUD 模式已经够用 |
| 引入 MVC 框架 | Next.js App Router 本身就是组件驱动的，MVC 的 View 层已被 React 组件替代 |
| 全面 SSR/SSG 改造 | 见下方详细分析 |

### 关于 SSR/SSG

本项目是一个**团队内部协作工具**，核心特征：

1. **所有页面都需要认证** — 无法做 SSG（静态页面不带用户数据）
2. **数据高度动态** — 任务、项目随时变化，无法预渲染
3. **无 SEO 需求** — 内部工具不需要搜索引擎收录
4. **客户端状态为主** — 拖拽、视图切换、过滤等都是客户端交互

当前所有页面都是 `"use client"` 是**合理的选择**。唯一可以优化的是：

- **登录页**可以做 SSR，服务端检查 cookie 后直接 redirect
- **首页认证检查**可以用 Next.js Middleware 替代客户端检查，减少白屏时间

但这些是边际优化，不值得大规模重构。
